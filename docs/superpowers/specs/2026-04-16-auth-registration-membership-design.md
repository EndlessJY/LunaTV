# LunaTV 登录、注册、邀请码与会员有效期设计

## 背景

当前 LunaTV 已具备基础登录、注册与后台用户配置能力，但缺少以下能力：

- 游客跳过登录后的受限访问能力
- 当前页登录/注册弹窗切换体验
- 基于邀请码的注册控制
- 基于会员有效期的账号生命周期管理
- 过期宽限期与自动清退机制
- 面向后续商业化的邀请码管理基础设施

本设计目标是在不一次性扩展为完整支付/订单系统的前提下，建立一套可持续演进的“游客访问 + 账号有效期 + 邀请码发放”模型。

## 本轮目标

- 登录页增加“跳过”按钮，允许用户以游客态进入首页
- 游客可浏览首页、搜索、详情、播放页
- 游客在触发播放、切集或写入行为时，在当前页面弹出登录/注册弹窗
- 已有账号用户可直接登录
- 注册用户可在登录弹窗内切换到注册弹窗
- 后台支持两个开关：
  - 允许注册
  - 注册需要邀请码
- 超级管理员后台支持邀请码的新增、生成、禁用、删除与查看
- 邀请码支持两类时效：
  - 邀请码本身有效期
  - 邀请码注册后带来的账户有效期
- 普通用户和普通管理账号受账户有效期控制，`owner` 永不过期
- 过期账号在宽限期内保留只读访问，宽限期结束后自动删除账号及其全部用户数据

## 非目标

- 本轮不实现支付系统
- 本轮不实现订单系统
- 本轮不实现完整续费后台与对账能力
- 本轮不实现短信、邮件或站内消息提醒系统
- 本轮不实现邀请码分销、批次报表与财务统计

## 用户状态模型

前端访问态分为以下几类：

- `guest`：用户主动点击“跳过”后进入的游客态
- `authenticated`：已登录且账号有效
- `expired`：已登录但账号已过期，仍处于宽限期内
- `owner`：站长账号，永不过期

说明：

- `guest` 不是单纯的“未登录”，而是明确的已跳过状态，需要被前端持久化记录，便于控制弹窗和拦截体验
- `expired` 用户允许继续浏览只读页面，但不能执行播放与写入
- `owner` 不受会员体系限制

## 页面访问与操作权限

### 允许游客访问的页面

- 首页
- 搜索页
- 详情页
- 播放页

### 游客受限的行为

以下行为在游客态下不能直接执行，应在当前页面弹出登录/注册弹窗：

- 开始播放
- 切换剧集
- 收藏
- 保存播放记录
- 保存或写入搜索历史
- 写入跳过片头片尾配置
- 其他依赖用户身份的写操作

### 过期用户受限的行为

过期但仍在宽限期内的用户：

- 可登录
- 可浏览首页、搜索、详情、播放页
- 触发播放、切集和任意写操作时，在当前页面弹出“账号已过期”提示

该提示需明确展示：

- 账号已过期
- 剩余宽限期天数
- 若未及时续费，账号与用户数据将被删除

## 登录与注册交互

### 登录页

登录页新增“跳过”按钮。

用户点击后：

- 写入游客态标记
- 跳转到首页

### 当前页弹窗

统一使用一个认证弹窗容器，支持两种模式：

- `login`
- `register`

交互规则：

- 游客触发受限操作时，弹出认证弹窗，默认显示登录模式
- 登录模式提供“去注册”入口
- 注册模式提供“去登录”入口
- 若后台关闭“允许注册”，前台不展示注册入口

### 注册弹窗字段

- 用户名
- 密码
- 邀请码

邀请码字段规则：

- 若后台关闭“注册需要邀请码”，邀请码字段可隐藏或显示为非必填
- 若后台开启“注册需要邀请码”，邀请码字段为必填，且必须通过服务端校验

## 后端账号模型扩展

现有用户配置模型需要扩展以下字段：

- `expiresAt`：账户到期时间
- `graceDeleteAt`：账号计划删除时间，可由 `expiresAt + 宽限期天数` 动态推导，也可在运行时计算

角色规则：

- `owner`：永不过期
- `admin`：受有效期控制
- `user`：受有效期控制

续期规则预留如下：

- 若账号未过期，续期时从原 `expiresAt` 顺延
- 若账号已过期，续期时从当前时间开始重新计算

即：

- 未过期：`newExpiresAt = oldExpiresAt + duration`
- 已过期：`newExpiresAt = now + duration`

## 后台系统开关

后台新增并维护以下站点级开关：

- `AllowRegister`：允许注册
- `RequireInviteCodeForRegister`：注册需要邀请码
- `ExpiredGracePeriodDays`：账号过期后的宽限期天数

规则：

- `AllowRegister = false` 时，前台隐藏注册入口，接口拒绝注册
- `AllowRegister = true` 且 `RequireInviteCodeForRegister = false` 时，允许无邀请码注册
- `AllowRegister = true` 且 `RequireInviteCodeForRegister = true` 时，注册必须提供有效邀请码
- `ExpiredGracePeriodDays` 为自定义整数天数，建议后台校验最小值为 `1`

## 邀请码模型设计

邀请码必须作为独立实体进行管理，而不是配置字符串列表。

建议结构如下：

- `code`：邀请码内容
- `status`：`active | used | disabled`
- `createdAt`
- `createdBy`
- `note`：备注，可选
- `inviteExpiresAt`：邀请码自身截止时间
- `accountDurationDays`：注册成功后赋予账户的有效天数
- `usedBy`：使用该邀请码注册的用户名
- `usedAt`

说明：

- 邀请码本身有效期使用绝对时间 `inviteExpiresAt`
- 账户有效期使用相对时长 `accountDurationDays`
- 选择“绝对时间 + 相对时长”的组合，是为了兼顾商业化可运营性与后续续费复用能力

## 邀请码校验规则

当注册需要邀请码时，服务端需要按以下顺序校验：

1. 邀请码必须存在
2. 邀请码状态必须为 `active`
3. 当前时间必须早于或等于 `inviteExpiresAt`
4. 邀请码必须尚未被使用

注册成功后：

- 创建用户
- 计算用户 `expiresAt`
- 将邀请码标记为 `used`
- 写入 `usedBy` 和 `usedAt`

账户有效期计算：

- 新注册用户：`expiresAt = now + accountDurationDays`

## 超级管理员邀请码后台

邀请码管理仅对超级管理员开放。

后台支持：

- 手动新增邀请码
- 批量生成邀请码
- 删除邀请码
- 禁用邀请码
- 查看邀请码状态
- 查看邀请码创建时间
- 查看邀请码本身有效期
- 查看邀请码对应账户有效期时长
- 查看邀请码备注
- 查看邀请码是否被使用、被谁使用、何时使用

### 批量生成能力

批量生成时支持设置：

- 生成数量
- 邀请码本身有效期
- 账户有效期天数
- 可选备注

这样可覆盖后续常见场景：

- 测试邀请码
- 活动邀请码
- 销售卡密
- 不同时长的会员码

## 账号过期与宽限期

### 状态定义

账号生命周期按以下阶段流转：

- 正常：`now <= expiresAt`
- 已过期：`now > expiresAt` 且 `now <= expiresAt + gracePeriod`
- 已清退：`now > expiresAt + gracePeriod`

### 过期用户行为

在宽限期内：

- 允许登录
- 允许浏览只读页面
- 禁止播放与写操作
- 在当前页面弹出“账号已过期”提示

提示内容需要包含：

- 账号已过期
- 还剩多少天自动删除
- 若不续费，账号与数据将被清空

### 自动删除策略

当账号超过宽限期仍未续费时：

- 删除账号
- 删除收藏
- 删除播放记录
- 删除搜索历史
- 删除跳过片头片尾配置
- 删除其他用户维度数据

本设计采用硬删除，不保留恢复入口。

## 删除执行策略

为了避免只依赖单一调度机制，删除采用双层保障：

### 访问时顺手清理

用户发起读写请求时，如果服务端发现该账号已超过宽限期：

- 立即执行账号删除
- 返回未授权或账号已失效状态

### 定时清理

保留一个定时任务入口，用于周期性扫描并清理已超过宽限期的账号，作为兜底机制。

这样即使没有稳定的 cron，也不会长期保留应删除未删除的数据。

## 前后端拦截策略

### 前端

前端负责：

- 识别游客态标记
- 在受限操作触发时弹出登录/注册弹窗
- 对已登录但过期用户弹出到期提醒弹窗

前端不应单独作为最终权限判断来源。

### 后端

后端负责最终权限校验。

对写操作和播放相关关键接口统一校验：

- 未登录：返回未登录错误
- 已登录但已过期且仍在宽限期：返回“账号已过期”
- 已登录且已超过宽限期：先删除账号，再返回失效状态
- 已登录且有效：允许访问

这样可以确保：

- 前端体验统一
- 即便用户绕过前端，也无法越权写入或播放

## 第一阶段实施范围

本轮实施内容：

- 登录页“跳过”按钮
- 游客态标记
- 当前页登录/注册弹窗
- 游客对播放与写操作的拦截
- 后台两个开关：
  - 允许注册
  - 注册需要邀请码
- 后台宽限期配置：
  - 过期宽限期天数
- 邀请码管理后台：
  - 手动新增
  - 批量生成
  - 禁用
  - 删除
  - 列表展示
- 注册时邀请码校验
- 用户 `expiresAt` 写入
- 登录后识别过期状态
- 过期用户在当前页收到弹窗提示
- 宽限期超时后自动删除账号及全部用户数据

## 第二阶段预留

后续单独迭代：

- 已有账号续费入口
- 使用邀请码给已有账号续期
- 后台手动给用户延长有效期
- 到期提醒体系
- 邀请码批次管理
- 报表和统计
- 商业化支付闭环

## 兼容性与风险

### 兼容性

- 现有 `owner` 登录逻辑需保持兼容
- 已存在普通用户若没有 `expiresAt`，需要定义迁移策略
- 明确迁移策略：现有非 `owner` 用户如果没有 `expiresAt`，默认视为历史用户长期有效，不在本轮自动判定为过期，后续如需纳入会员体系，由后台单独处理或后续迁移脚本处理

### 风险

- 当前项目缺少测试，认证与清理逻辑回归风险较高
- 游客拦截如果仅做前端不做服务端兜底，会存在越权风险
- 自动删除一旦触发无法恢复，需要后台文案和提示足够明确
- 邀请码和用户时效进入配置后，需要注意缓存一致性与配置刷新策略

## 测试重点

实施阶段重点验证：

- 跳过登录后的游客访问路径
- 游客在播放、切集、收藏、保存记录时是否稳定弹窗
- 注册开关和邀请码开关的各种组合行为
- 邀请码过期、已使用、禁用等分支
- 新用户注册后 `expiresAt` 是否正确
- 普通用户过期后是否正确进入受限模式
- 超过宽限期后是否正确清理账号与数据
- `owner` 是否始终不受限

## 推荐实施原则

- 先统一状态模型，再改页面交互
- 先做后端权限与数据模型，再接前端弹窗
- 所有关键限制以后端校验为准
- 把邀请码视为独立业务对象，而不是注册表单上的一个附加字段
